## 0. Purpose

This document is the governing build constitution for the current Rosetta/Entif implementation era. Its job is to stop architectural drift, freeze the most important ratified decisions, and translate prior synthesis into binding engineering law.

It is not a visionary essay.  
It is not a replacement for Rosetta v3.0.0, ROCK-31XX, or the Secure Architecture Companion.  
It is the staging doctrine that tells the repo what counts, what comes first, what is deferred, and what must never silently blur.

## 2. Standardized terminology

### 2.1 Required distinctions
- **Semantic latticing** = the process of semantic compression, linkage, disambiguation, and structured weaving.
- **Cognitive tapestry** = the compiled bounded artifact produced by semantic latticing.
- **Receipt-bundle tapestry** = the specific tapestry profile used for verification closure.
- **Constitutional Bootstrap** = the smallest honest proof of the Rosetta/Guard/Receipt loop.
- **Text-Core MVP** = the first practical ingest-and-interpret rung for heterogeneous text sources.
- **MVP Alpha RC** = the true alpha release candidate threshold, broader than the bootstrap loop.
- **Plane 1 memory** = Rosetta constitutional truth/provenance layer.
- **Plane 2 memory** = temporal state/history layer.
- **Plane 3 memory** = activation/relevance/recall layer.

### 2.2 Forbidden conflations
The following must remain distinct:
- raw signals vs. interpretations
- observations vs. conjectures
- core semantics vs. pack semantics
- truth store vs. cache/index
- parse-only ingest vs. side-effecting command execution
- design donor methodology vs. constitutional substrate
- bootstrap proof vs. alpha RC

## 3. Staging doctrine: the three-rung staircase

## 3.1 Rung A: Constitutional Bootstrap
Purpose: prove the blood chemistry of the system, not broad usefulness.

Mandatory scope:
- canonicalization
- CID minting
- schema validation
- receipt emission
- receipt-bundle / tapestry verification
- guard decision tokens
- guarded no-side-effect toolcall
- replay/tamper tests
- CLI/API proof path

Non-goals:
- real productivity orchestration
- rich UI
- temporal graph memory
- activation memory
- source ingestion breadth
- multimodal input
- distributed swarm functions

## 3.2 Rung B: Text-Core MVP
Purpose: become recognizably useful on real heterogeneous text sources.

Mandatory scope:
- ingest multiple structurally distinct text-source families
- deterministic ingress refinery
- source → observation → interpretation → tapestry progression
- rights-scoped retrieval
- English accompaniment for promoted artifacts (minimum viable coverage)
- receipt emission on all meaningful promotions
- Postgres/pgvector baseline introduced before serious RC claims

Non-goals:
- multimodal media semantics beyond text extraction
- distributed cognition
- fully autonomous persona ecosystems
- broad voice daemon as a release gate

## 3.3 Rung C: MVP Alpha RC
Purpose: satisfy the true ratified threshold.

Mandatory scope:
- heterogeneous text-source families ingest reliably
- Ithkuil grammar corpus is processed to a satisfactory interpretability threshold
- lexical anchor mapping exists where appropriate
- every relevant tile and compiled tapestry exposes English-language accompaniment
- temporal memory plane demonstrably improves stateful recall
- activation memory plane demonstrably improves “right memory first”
- receipt-bundle verification exists for meaningful audited claims
- mission-control/inspection view is usable
- conformance + migration tests pass

This is the real alpha threshold.  
The older tiny dry-run-only “alpha” notion is formally demoted to bootstrap proof.

## 4. Receipt law

### 4.1 Constitutive principle
For Rosetta/Entif purposes, no meaningful artifact or meaningful transform is valid without a receipt path.

This includes:
- ingest promotions
- schema-aware routing choices
- classification decisions
- dedupe/revision resolutions
- lexical/conceptual mappings
- tapestry compilations
- guard decisions
- evaluations
- migrations/translators
- externally asserted “verified” claims

### 4.2 Practical posture
The conceptual execution spine remains useful:
`Run → Action → ToolCall → Observation → Evaluation`

But implementation law is stricter:
- every meaningful step must emit or be bound to a receipt artifact
- every verified claim must be supportable via receipt-bundle closure
- receipt absence is a failure condition, not a logging omission

### 4.3 RRP content posture
RRP content model wins over generic receipt hand-waving. The standard payload shape should prioritize:
- `subjects`
- `claims`
- `digests`
- `policy_refs`
- `nonce`
- `auth`
- `sig`
- bundle closure metadata

## 5. Storage, memory, and data-plane law

### 5.1 Storage by phase
**Bootstrap:**  
- content-addressed local store
- SQLite index acceptable and preferred for simplicity

**Text-Core / Alpha RC:**  
- Postgres JSONB + RLS/rights enforcement
- pgvector for portable vector baseline
- graph and activation layers as sidecars/adapters or native imitations

### 5.2 Memory plane separation
**Plane 1: Rosetta truth/provenance plane**  
Immutable receipted tiles, policies, receipts, compiled tapestries, lineage, and verification closure.

**Plane 2: Temporal state/history plane**  
Adopt patterns such as:
- episodic ingest
- temporally aware relations
- historical truth handling
- evolving-state recall
- hybrid search across time/text/semantics/graph

**Plane 3: Activation/recall plane**  
Adopt patterns such as:
- recency/frequency-aware scoring
- association-weight updates
- conflict-aware confidence modulation
- total-recall preservation
- proactive/trigger-style relevance

### 5.3 Pruning law
Never delete truth-store tiles to simulate forgetting.  
Prune indexes, caches, activation priorities, and derived projections.  
Long-tail retrieval may cool; it must not silently disappear from the constitutional truth layer.

## 6. Input and refinement law

### 6.1 Text-only-first is binding
The first serious RC is text-first. Video, audio, image, and other media may participate only via extracted text until later phases.

### 6.2 Ingress refinery is Pillar Zero
Before costly semantic hydration, perform cheap deterministic work first:
- normalization
- hashing
- dedupe
- revision detection
- source typing
- metadata extraction
- policy/safety screening
- promotion gating
- candidate-tapestry planning

### 6.3 Raw capture preservation
Raw source evidence is always preserved as source/episode material and never overwritten by later interpretation.

### 6.4 Ambiguity law
Ambiguity must produce conjectures, alternatives, or pending-confirmation artifacts rather than fake certainty.

---

## 7. Execution, safety, and rights

### 7.1 Parse-only by default
Ambient or passive ingest operates in parse-only mode by default. No side-effecting action is allowed without an explicit transition into action-authorized mode.

### 7.2 Guard law
All side-effecting execution must be mediated by the Guard.
Requirements:
- deny-by-default
- structured decision tokens
- short-lived expiry
- policy hash/version binding
- subject/tool/resource caps
- replay refusal
- admission checks in executors

### 7.3 Rights enforcement boundary
Rights must be enforced at retrieval/storage boundary.  
“Retrieve then filter later” is forbidden for sensitive or scoped data.

### 7.4 Identity-sensitive controls
Any person-modeling, simulation, stylometric identity, cognitive-twin, or impersonation-adjacent workflow must default to elevated policy, explicit classification, and human-in-the-loop authorization.

## 8. Repo/process doctrine

### 8.1 TS-first spine
TypeScript / Nx / pnpm is the constitutional implementation lane.

### 8.2 Python specialist lane
Python is allowed for:
- eval harnesses
- OCR/ASR
- embeddings/ML experiments
- corpus utilities
- graph experimentation
- other specialist workloads

But Python must not become a shadow constitution for core runtime, core schemas, guard, receipt, or tapestry law.

### 8.3 AI-readable repo rule
Every important package, pack, recipe, skill, and integration should be:
- machine-legible
- explicit about prerequisites
- explicit about acceptance conditions
- example-rich
- narrow in purpose
- traceability-headed where appropriate

### 8.4 Tool-budget discipline
Too many hot tools are a system smell. Tool budgets must be defined per role/session, routing ambiguity must be tested, and CRUD-ish surfaces should be consolidated where that improves clarity.

## 9. ADR register

### ADR-0001: Authority hierarchy
**Status:** Accepted  
**Decision:** constitutional > implementation > expansion > design donor  
**Consequence:** later synthesis cannot silently override Rosetta/ROCK/Guard law.

### ADR-0002: Receipt primacy
**Status:** Accepted  
**Decision:** no meaningful artifact or meaningful transform exists without receipt path  
**Consequence:** receipt emission becomes a first-class acceptance gate.

### ADR-0003: Three-rung staircase
**Status:** Accepted  
**Decision:** Bootstrap, Text-Core, Alpha RC are separate thresholds  
**Consequence:** prevents false alpha claims and keeps bootstrap honest.

### ADR-0004: Semantic latticing vs. cognitive tapestry
**Status:** Accepted  
**Decision:** process vs. artifact split is standardized  
**Consequence:** terminology becomes operationally useful instead of noisy.

### ADR-0005: Storage by phase
**Status:** Accepted  
**Decision:** CAS+SQLite for bootstrap; Postgres+pgvector by serious RC; temporal/activation sidecars thereafter  
**Consequence:** resolves fake binary between local-first bootstrapping and mature storage.

### ADR-0006: Memory-plane separation
**Status:** Accepted  
**Decision:** truth/provenance, temporal state, and activation recall are separate planes  
**Consequence:** avoids shoving all memory semantics into one slippery substrate.

### ADR-0007: Text-only-first
**Status:** Accepted  
**Decision:** MVP scope is text-first across heterogeneous text classes  
**Consequence:** multimodal ambitions cannot derail alpha staging.

### ADR-0008: Ingress refinery as Pillar Zero
**Status:** Accepted  
**Decision:** cheap-first refinement is mandatory before richer semantic promotion  
**Consequence:** token economy and correctness are structurally favored.

### ADR-0009: Parse-only default and guard-mediated side effects
**Status:** Accepted  
**Decision:** parse-only unless explicitly authorized; guard mediates every side effect  
**Consequence:** reduces accidental autonomy and aligns with zero-trust posture.

### ADR-0010: Rights at retrieval boundary
**Status:** Accepted  
**Decision:** scoped retrieval enforces policy before data leaves storage  
**Consequence:** no retrieve-then-filter anti-pattern.

### ADR-0011: TS-first spine, Python specialist lane
**Status:** Accepted  
**Decision:** TS governs runtime spine, Python stays specialist  
**Consequence:** stack bifurcation is contained.

### ADR-0012: OB1 as process donor only
**Status:** Accepted  
**Decision:** import contribution grammar and workflow methodology, not ontology or platform gravity  
**Consequence:** Rosetta/Entif retain constitutional primacy.

### ADR-0013: Tool-budget doctrine
**Status:** Accepted  
**Decision:** tool-surface size becomes a measurable systems concern  
**Consequence:** routing ambiguity and context waste are treated as regressions.

### ADR-0014: Identity-sensitive governance
**Status:** Accepted  
**Decision:** personhood-level modeling is a first-class governance risk  
**Consequence:** future persona work inherits elevated safety controls.
