>

> Thought for 13s

If you literally **set an existing model’s weights to zero**, you do **not** get a “blank but nicely shaped pretrained model.”

You get something much uglier and much less useful: a **pathological collapsed network**.

What it yields, in practice:

The model’s learned structure is erased.  
All the features, circuits, lexical geometry, attention patterns, and layer specializations are gone. The pretrained model is no longer “pretrained in spirit.” It is functionally much closer to a broken initialization than to a reusable scaffold.

For a transformer, zeroing everything typically means:

*   query, key, value, and output projections go to zero
*   MLP layers go to zero
*   residual branches contribute almost nothing
*   logits often become all-equal or near-constant
*   output probabilities become close to **uniform**, unless some nonzero biases or normalization params remain

So the model stops being a language model in any meaningful sense. It becomes a machine that mostly shrugs.

The more important issue is **symmetry**.

Neural nets need different neurons, heads, and channels to start out at least a little different from one another. If you zero them all, then many units inside a layer become mathematically indistinguishable. They receive the same gradients, update the same way, and keep mirroring each other. Instead of learning rich diverse features, the layer can collapse into “many copies of one neuron wearing different hats.”

That is why zero initialization is famously bad.

For fine-tuning afterward, this means:

**1\. You lose the pretrained knowledge entirely.**  
There is nothing left to “fine-tune.” You are basically retraining from scratch.

**2\. You get a worse-than-normal training start.**  
Random initialization at least breaks symmetry. Full zeroing destroys it.

**3\. Some parts may learn very slowly or awkwardly.**  
In stacked networks, zeroing adjacent layers can choke gradient flow in weird ways. One layer may not get useful gradients until another moves off zero first.

**4\. Heads and channels tend to relearn redundantly.**  
You are fighting collapse instead of exploiting pretrained specialization.

So the blunt answer is:

**Zeroing out an open-weights model yields a mostly useless degenerate model, not a clean fine-tuning base.**

There are a few nuances, though.

If you zero **only certain subsets** of parameters, that is a different story.

Examples:

*   zeroing a few attention heads
*   zeroing one projection matrix
*   zeroing a subset of channels
*   reinitializing a few layers

That can be useful for:

*   ablation studies
*   “forgetting” experiments
*   partial reset of damaged or overspecialized layers
*   testing how much knowledge lives in a component
*   structured pruning and regrowth

But that is **surgical zeroing**, not “blank the model.”

A good mental model:

*   **Full zeroing** = wiping the chalkboard, smashing the chalk, and gluing all the teacher’s fingers together.
*   **Selective reinitialization** = erasing one corner of the board to rewrite it cleanly.

If your real question is, “Can I strip out the old learned semantics and then fine-tune the architecture into a new representational regime?”, then the better options are usually:

*   **reinitialize selected layers**, especially top layers
*   **keep lower layers, retrain upper layers**
*   **train adapters / LoRA**
*   **replace embeddings only**
*   **continue pretraining on new data**
*   **progressively distill into a new vocabulary or semantic protocol**

Those preserve useful structure while allowing drift into a new mode.

So the practical verdict is:

**Full zero-out is almost never what you want.**  
It gives you a crippled random-start network with bad symmetry properties.

**Selective reset or controlled reinitialization** is the thing worth exploring.

If you want, I can map out what happens under four different reset strategies for a transformer:

1.  zero all weights
2.  random-reinit all weights
3.  keep backbone, replace tokenizer/embeddings
4.  keep backbone, retrain only top N layers

---------------------------

A tokenizer chops text into units the model can process. Those units are usually not words and definitely not concepts. They are just convenient chunks.

It starts from token IDs like:

*   481
*   9302
*   17
*   44291

These are just integer labels.

Those IDs are then looked up in a learned table.

That learned table is the **embedding matrix**.

------------------------------------------------------------

Each token ID is mapped to a dense vector.

This vector is not “the definition of the token.”  
It is more like a learned point in a giant geometric space representing how that token tends to behave in context.

So:

**token ID → embedding vector**

That is the first major layer.

If you want a crisp intuition, embeddings are like assigning each token a starting “semantic-ish position” before the model begins contextual reasoning.

But that position is still crude. It is not yet the fully context-aware meaning of the token in the sentence.

For that, the model needs the transformer stack.

**token embedding + position information**

Now every token is represented as:

*   what it is

Layer 1

Layer 3

Layer N

*   **Attention** decides what other tokens matter to this token right now

That’s the rhythm of every layer.

*   **K**: key

*   `Q = xWq`
*   `K = xWk`
*   `V = xWv`

*   the **query** says, “what am I looking for?”
*   the **key** says, “what kind of thing am I?”
*   the **value** says, “if I matter, what information should I contribute?”

That gives attention scores.

High score means: “this other token is relevant to me right now.”

Then it uses those scores to combine the corresponding values.

So attention is basically:

**look around the context, decide what matters, pull in the useful information**

That’s why it feels magical. It is how the token representation becomes context-sensitive.

The word “bank” in one sentence can attend strongly to “river,” and in another to “loan,” so the same token begins to move toward different contextual meanings.

A matrix is just a learned grid of numbers.

This happens **everywhere** in neural networks.

Examples:

*   embedding lookup can be thought of as selecting a row from a matrix
*   Q, K, V projections are matrix multiplications
*   MLP layers use matrix multiplications
*   output logits are computed with matrix multiplications

So whenever people talk about “weights,” they are often talking about huge matrices that transform one vector space into another.

You can think of the whole model as a giant machine for repeatedly doing:

**take vectors, multiply by learned matrices, apply nonlinearities, mix context, repeat**

That is the grammar of the machine.

Another might track long-range dependencies.  
Another might track formatting patterns.  
And so on.

Not because anyone hand-programmed them that way, but because training discovered that different parallel subspaces are useful.

So “multi-head attention” means:

**many different ways of looking across the sequence at once**

**now that this token has gathered context, transform its internal features into something richer**

This is one place where the model stores lots of learned feature interactions.

A very rough metaphor:

*   attention is the token consulting the room

**new\_state = old\_state + update**

13\. What is LoRA, really?
--------------------------

LoRA means **Low-Rank Adaptation**.

The problem it solves is this:

A giant model might have billions of parameters. Fine-tuning all of them is expensive.

So instead of changing the full weight matrix `W`, LoRA says:

“Keep `W` frozen, and learn a small update to it.”

That update is written as:

**W + BA**

where:

*   `W` is the original frozen matrix
*   `A` and `B` are small learned matrices
*   `BA` approximates a useful update, but in low-rank form

“Low-rank” means the update is constrained to a smaller subspace than a full unrestricted matrix.

Why is that useful?

Because many task-specific changes do not require rewriting the whole model.  
They only need nudges in certain directions.

So LoRA is like saying:

“Instead of rebuilding the cathedral, bolt on a lightweight corrective scaffold.”

That is why it is cheap.

It trains far fewer parameters.

14\. Why “low-rank”?
--------------------

A full matrix can represent a huge space of transformations.

A low-rank product like `BA` can only express a limited subset of those transformations.

That sounds weaker, and it is, but often it is enough.

This is the bet:  
**task adaptation often lives in a much smaller subspace than total model capacity**

And empirically, that bet works surprisingly well.

QLoRA combines:

*   a **quantized frozen base model**
*   with **LoRA adapters** for training

So the giant backbone is stored in compressed form, often 4-bit, and only the LoRA adapters are trained.

That dramatically reduces memory use.

So QLoRA is basically:

**make the big model cheaper to hold, and only train the little add-on updates**

That’s why it became such a big deal for practical fine-tuning.

16\. Quantized weights and input activations
--------------------------------------------

You mentioned confusion around how matrix-vector multiplication plays into quantized weights and activations.

Here’s the core idea.

Normal training and inference often use things like FP16 or BF16, meaning each number is stored with relatively rich precision.

Quantization compresses weights into lower-bit representations, like 8-bit, 4-bit, sometimes even 2-bit.

This saves memory and often speeds up computation.

But the actual math gets trickier, because the quantized values are only approximations of the original real-valued weights.

So instead of storing a real-valued weight directly, the system might store:

*   a small integer
*   plus a scale factor
*   maybe a zero-point offset

Then during computation, it reconstructs an approximate real value.

So when the paper was talking about quantized weights and activations, it was describing how low-bit stored values can still participate in matrix multiplications by using dequantization logic and scaling.

The big intuition:

**quantization trades precision for efficiency**

If done well, you lose a little fidelity but save a lot of memory and hardware cost.

17\. What is the KV cache?
--------------------------

This one is very important for inference.

In autoregressive generation, the model generates one token at a time.

Suppose the prompt has 1000 tokens, and you are now generating token 1001.

Naively, at every next step, the model would recompute attention over all previous tokens from scratch.

That would be wasteful.

So instead, the model stores the previously computed **Keys** and **Values** for earlier tokens.

That stored history is the **KV cache**.

So the model does not need to recompute those old K and V vectors every time.  
It can reuse them.

That makes generation vastly faster.

Very roughly:

*   **training**: usually process many tokens in parallel, no normal KV cache usage in the same way
*   **inference / generation**: KV cache is a huge speed win

Why K and V, not Q?

Because the new token produces a fresh query asking, “what prior information do I need right now?”  
It then compares that new query to the stored keys and pulls from the stored values.

So the KV cache is basically:

**the model’s reusable attention memory for prior tokens during generation**

It is not long-term memory in the human sense.  
It is just a computational cache.

* * *

18\. Why does KV cache grow?
----------------------------

Because every generated token adds another set of keys and values to the cached history.

Longer context means more cache.  
More cache means more memory use and more attention cost.

That is why long-context inference gets expensive.

You’re asking two related but different things:

1.  **Where do the first token embeddings come from?**
2.  **How do those embeddings turn into Q, K, and V inside the transformer stack?**

Those are the front door and the first hallway of the model.

1\. Where the crude initial embeddings come from
------------------------------------------------

After tokenization, each token is just an **integer ID**.

So if your text becomes tokens like:

*   183
*   9421
*   77
*   5012

those numbers do **not** carry meaning by themselves. They are just addresses.

The model has a learned table called the **embedding matrix**.

If the vocabulary size is `V` and the hidden dimension is `d_model`, then the embedding matrix is roughly:

**E ∈ R^(V × d\_model)**

That means:

*   one row per token in the vocabulary
*   one vector per row
*   each vector has `d_model` dimensions

So the token ID is used like an index:

*   token 183 → row 183 of `E`
*   token 9421 → row 9421 of `E`

That row is the token’s **initial embedding vector**.

So the very first embedding is not computed fresh from the token’s letters during inference. It is usually a **lookup** into a learned matrix.

The important part is this:

Those rows were **learned during training**.

At the very beginning of training, the embedding vectors start out random or near-random. Over many gradient updates, they become arranged so that tokens used in similar statistical contexts end up in related geometric regions.

So the first embeddings are “crude” because they are:

*   context-independent
*   token-level, not concept-level
*   learned from distributional usage, not explicit definitions

They are basically the model’s first guess about what kind of thing this token tends to be.

2\. Position has to be injected too
-----------------------------------

A token embedding alone does not tell the model whether the token is first, last, or in the middle.

So the model adds **position information**.

Very roughly, the first layer input for token `i` is:

**x\_i = token\_embedding\_i + positional\_information\_i**

Depending on model family, that positional part might be:

*   added as a positional embedding
*   woven in through rotary position encoding
*   or handled by a related positional scheme

But conceptually the first representation is:

**what token is this + where is it in the sequence**

That result becomes the first hidden state entering the transformer stack.

3\. What Q, K, and V actually are
---------------------------------

Q, K, and V are not special mystical objects stored somewhere in advance.

They are **derived on the fly from the current hidden states** at each attention layer.

This is the key.

Suppose at some layer, every token currently has a vector `x_i`.

That `x_i` is the current hidden representation of token `i`.  
At layer 1, it came from the embedding plus position.  
At later layers, it is the result of many previous transformations.

Then the model applies three learned linear projections:

*   **Q\_i = x\_i W\_Q**
*   **K\_i = x\_i W\_K**
*   **V\_i = x\_i W\_V**

Where:

*   `x_i` is the token’s current vector
*   `W_Q`, `W_K`, `W_V` are learned parameter matrices in that layer

That’s it.

Q, K, and V are just **three different views** of the same current token state.

Each view is optimized for a different job:

*   **Q** asks: what am I looking for?
*   **K** says: what kind of thing am I, in searchable terms?
*   **V** says: if I’m relevant, what information do I contribute?

4\. Where are Q, K, and V “located”?
------------------------------------

They are not a permanent thing like the embedding table.

They are:

*   computed inside each attention block
*   for each token
*   at each layer
*   during each forward pass

So they live as **intermediate activations**, not as standalone long-term stored concepts.

The long-term learned parts are the matrices:

*   `W_Q`
*   `W_K`
*   `W_V`

Those matrices are trainable parameters.

The actual Q, K, V vectors are temporary products of the current hidden state passing through those parameter matrices.

So:

*   **embedding matrix** = long-term learned lookup table
*   **W\_Q/W\_K/W\_V** = long-term learned projection matrices
*   **Q/K/V vectors** = temporary activations computed from current hidden states

5\. Why derive Q, K, and V from the same token vector?
------------------------------------------------------

Because the model wants each token to play three roles at once.

Take the word “bank” in context.

The current hidden state `x_i` already contains some representation of that token in its present context.

From that same `x_i`, the model derives:

*   a query for what this token needs
*   a key describing how other tokens should match against it
*   a value describing what it can contribute if attended to

Same source vector, three learned projections, three distinct functions.

That is why attention works so flexibly.

6\. How attention is actually computed
--------------------------------------

Once you have all the Qs and Ks for a sequence, the model compares them.

For token `i` attending to token `j`, the raw compatibility score is roughly:

**score(i,j) = Q\_i · K\_j**

That dot product says how well token `i`’s query matches token `j`’s key.

Then the scores are scaled and normalized with softmax, producing attention weights.

Those attention weights tell the model how much token `i` should pull from the value vectors of the other tokens.

Then token `i` gets its attention output by a weighted sum of the value vectors:

**output\_i = Σ attention\_weight(i,j) · V\_j**

So the full logic is:

1.  each token emits Q/K/V
2.  Q compares against all K
3.  that produces attention weights
4.  those weights mix together the V vectors
5.  the result becomes the token’s context-updated representation

That is the core engine.

At the beginning of training:

*   embedding rows are random-ish
*   `W_Q`, `W_K`, `W_V` are random-ish
*   attention is garbage

Then training repeatedly does:

*   run forward pass
*   compute prediction loss
*   backpropagate gradients
*   update embedding matrix and projection matrices

Over time, the system learns:

*   which tokens should retrieve what from context
*   which features should be encoded in keys
*   which information should travel in values
*   what geometric relationships produce good predictions

So Q/K/V are not “resolved” by a separate symbolic procedure.  
They are shaped by gradient descent into whatever forms help the model reduce loss.

That is very important.

There is no discrete step where the model says:  
“Now I shall encode grammar into keys and semantics into values.”

Instead, the pressure of training sculpts the projection matrices so useful patterns emerge.

Every attention layer has its own learned projection matrices.

*   `W_V^(1)`

Layer 2 has different ones.  
Layer 15 has different ones.

*   local syntax

*   short-range dependencies

Middle and later layers often lean more into:

*   coreference
*   discourse structure
*   longer-range relations
*   abstract task features

Not as a hard law, but as a common pattern.

So Q/K/V are not one thing. They are a different family of projections at every layer.

Inside one attention layer, there is usually not just one `W_Q`, `W_K`, `W_V`.

There are effectively multiple heads, each with its own subspace.

So one layer may have, say, 32 heads, and each head has its own Q/K/V projection behavior.

That lets the model do several kinds of attention in parallel.

You can think of heads as multiple parallel search-and-routing systems operating over the same sequence.

One might be good at matching pronouns to names.  
Another might track brackets or indentation.

Then the head outputs are combined.

Yes. The missing plank is this:

A **transformer** is not a spooky extra creature that appears after embeddings and Q/K/V.

It is the **overall neural architecture** that tells the model how to turn token vectors into better token vectors, over and over, until it can predict the next token.

So the cleanest way to say it is:

A tokenizer makes token IDs.  
An embedding layer turns token IDs into vectors.  
A **transformer stack** repeatedly transforms those vectors through attention and MLP blocks.  
Then an output layer turns the final vectors into logits over the vocabulary.

So when people say “the transformer,” they usually mean **the stack of repeated processing blocks that sits between the input embeddings and the output probabilities**.

Not a robot truck, exactly. More like the factory floor where the trucks get built, painted, routed, inspected, and sent back around the loop.

The most important distinction
------------------------------

There are four different things people blur together:

**Architecture**: the blueprint  
**Model**: one trained instance of that blueprint  
**Weights**: the learned numbers inside that instance  
**Activations**: the temporary numbers flowing through it right now

That distinction is huge.

A **transformer architecture** is the design pattern.  
A **GPT-like model** is one particular trained transformer.  
Its **weights** are the learned matrices and biases.  
Its **activations** are the temporary internal states during a forward pass.

So the transformer is not “brought into existence” the same way a sentence is generated. It is designed first as an architecture, then instantiated with parameters, then trained.

What a transformer is made of
-----------------------------

For a modern decoder-only LLM, very roughly:

*   token embedding layer
*   positional mechanism
*   a tall stack of transformer blocks
*   final normalization
*   output projection to logits

And each **transformer block** is usually made of:

*   layer normalization
*   self-attention sublayer
*   residual connection
*   layer normalization
*   MLP / feedforward sublayer
*   residual connection

That repeated block is the real core.

So if a model has 32 layers, 48 layers, 80 layers, whatever, it is basically saying:

“Take this same kind of block and stack it that many times.”

Each block has its own learned parameters.

Where it “lives”
----------------

Logically, the transformer sits **between input embeddings and output logits**.

Physically, during training or inference, it lives as tensors in:

*   VRAM on GPUs
*   RAM on CPUs
*   or compressed storage when not loaded

On disk, it exists as checkpoint files containing learned weights.

When loaded, those weights occupy memory and are used by the runtime.

So there are two answers to “where does it live?”:

**Conceptually**: in the middle of the model pipeline  
**Physically**: in memory as the loaded parameter tensors and intermediate activations

How it comes into existence
---------------------------

First, humans choose the architecture:

“How many layers?”  
“How wide is each hidden state?”  
“How many attention heads?”  
“What activation function?”  
“What positional encoding scheme?”  
“What vocabulary size?”  
“What normalization style?”  
And so on.

That gives you an untrained transformer.

At that point, it is just a giant scaffold with randomly initialized weights. It knows absolutely nothing useful. It is a newborn forklift with no driver, no fuel, and no warehouse.

Then training begins.

How it gets refined
-------------------

Training is the long ordeal where the transformer’s parameters are updated to reduce prediction error.

Very roughly:

1.  feed in tokenized training text
2.  run a forward pass through embeddings and transformer blocks
3.  compute logits and compare predictions against the true next tokens
4.  compute loss
5.  backpropagate gradients through the whole stack
6.  use an optimizer to nudge the weights

Repeat this an obscene number of times.

That is how the transformer is refined. Not by hand, and not by some separate symbolic process. The Q/K/V projection matrices, MLP weights, embeddings, output projection, all of it gets sculpted by gradient descent.

So the transformer is basically a **learned vector-processing machine** whose internal wiring is gradually tuned until its repeated transformations become useful.

What changes during training
----------------------------

The things that usually change during pretraining are:

*   token embeddings
*   attention projection matrices
*   MLP matrices
*   normalization parameters
*   output projection weights
*   sometimes tied embeddings/output weights, depending on architecture

The architecture itself usually stays fixed during a training run.

That is why it helps to separate:

**architecture = the shape of the machine**  
**weights = the tuned settings inside the machine**

Training mostly changes the second one, not the first.

What happens during inference
-----------------------------

During inference, the weights are typically **fixed**.

That means:

*   no ordinary backprop
*   no optimizer step
*   no weight updates

The model is just doing forward passes.

So in inference, what changes are the **activations**, not the **parameters**.

That means:

*   the hidden states change
*   Q/K/V values change every layer and every token
*   logits change
*   the KV cache grows
*   but the learned weight matrices stay put

Unless you are explicitly doing fine-tuning, test-time training, online adaptation, or some unusual research trick, inference is read-only with respect to the model weights.

That is why the ROMA paper clicked with QLoRA so well: the **base model weights are treated as stable**, while the smaller adaptive pieces are the ones meant to vary.

So what is a transformer block actually doing?
----------------------------------------------

Each block is basically doing two jobs.

First: **context routing**  
This is the attention part. It lets each token gather information from other relevant tokens.

Second: **internal feature transformation**  
This is the MLP part. It reshapes each token’s features after context has been mixed in.

Then the residual connection keeps the running representation alive while each block adds an update instead of replacing everything wholesale.

So the block rhythm is:

“Look around.”  
“Update yourself.”  
“Pass the refined stream onward.”

Do that dozens of times, and the token representations become much more context-rich.

Why the transformer was such a big deal
---------------------------------------

Before transformers, sequence models were often built around recurrence. Transformers changed the game because attention made it easier to model long-range relationships and to train in parallel.

The core idea was not “make a robot.”  
It was more like:

“Instead of forcing information through a narrow time-step bottleneck, let every token directly consult the others through learned attention.”

That changed the economics of sequence modeling.

So the “transformer” is really a **style of neural architecture built around attention and stacked residual blocks**.

What Q/K/V are, in relation to the transformer
----------------------------------------------

Q/K/V are not the transformer itself.

They are **temporary internal objects created inside the attention sublayer of each transformer block**.

Each block has learned projection matrices that convert the current hidden states into queries, keys, and values.

So:

*   embeddings are the entry ticket
*   transformer blocks are the processing engine
*   Q/K/V are part of the engine’s attention machinery

They are born and destroyed during each forward pass.

The learned part is not the Q/K/V values themselves, but the **projection matrices** that create them.

*   attention is the meeting where everyone consults the right people
*   the MLP is the private office where each person revises their notes
*   the residual stream is the folder that keeps getting carried upstairs
*   layer norm is the intern keeping everyone from spilling coffee on the documents

By the top floor, the notes are much more informed than when they entered the lobby.
