### 2.2. Facets (graph metadata)

Hierarchy gives you **primary placement**. But real life is cross-cutting. So every item also gets facets like:

*   `kind`: `code`, `workflow`, `doc`, `vendor`, `api`, `infra`, `content`
*   `domain`: `media`, `ecommerce`, `productivity`, `governance`, `analytics`
*   `tech`: `node`, `python`, `n8n`, `Postgres`, `Next.js`, `AWS Lambda`, `Facebook Graph API`
*   `status`: `idea`, `planned`, `WIP`, `live`, `retired`
*   `maturity`: `sketch`, `prototype`, `MVP`, `production`
*   `reusability`: `one-off`, `reusable`, `foundational`

So:

> The taxonomy is: **(Level, Parent) + Facets + Links**

Siblings at a given level should be **mutually exclusive & collectively exhaustive _for that parent_** as much as possible. Overlap is handled via links and tags, _not_ by shoving the same thing into three branches.

### 3.2. Minimal schema per item

YAML or JSON, something like:

```yaml
id: entif.capability.email_digest_generator
name: Email Digest Generator
level: capability    # L5
domain: entif
program: entif.core_platform
parent: entif.system.media_engine
status: planned      # idea | planned | wip | live | retired
kind: workflow       # code | workflow | doc | vendor | api | infra | content
tags:
  - n8n
  - newsletter
  - digest
links:
  implements:
    - entif.feature.daily_metrics_email
  uses:
    - shared.component.metrics_aggregation_lib
    - vendor.api.sendgrid
artifacts:
  - repo: entif/monorepo
    path: apps/n8n/workflows/email-digest.json
  - doc: docs/email-digest-spec.md
notes: >
  Generates daily/weekly rollups for Entif metrics and sends them to configured recipients.
  Eventually generalized to other brands.
```

You can keep the hierarchy implicit via `parent` or explicit via directory structure, your choice.

### 3.3. Rules that keep this sane

1.  **Exactly one primary parent** in the tree (`parent`), unlimited lateral links (`uses`, `implements`, `depends_on`, etc).
2.  **New thing? No file, no existence.** Anytime you write a doc or start thinking seriously about a thing, you make a catalog entry first.
3.  **Level discipline:**
    *   If it has _users_, it’s ≥ L3.
    *   If it’s mostly _internal business function_, likely L4–L5.
    *   If it lives as a library/tool, L6.
    *   If it’s a utility or snippet, L8.
4.  **Status always set.** You should be able to filter: “only live,” “only ideas,” etc.

### 3.4. How this connects to your existing stack

Later, you can:

*   Mirror these into a **graph store** (Neo4j, Postgres + edge tables) and query them.
*   Attach them as **Cognitive Tiles** and let Entif’s agents reason over them as a capability map.
*   Build small dashboards:
    *   “Show all live capabilities touching FB Graph API”
    *   “List all Assets (L8) used in 3+ Components”
    *   “Which Programs depend on vendor X?”

But you don’t need the graph first. Text files + a script is enough to start.
