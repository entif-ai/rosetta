## Finding: RLM-001-H

**Topic:** RLM paradigm shift: external prompt mounting vs. traditional context feeding

**Raw findings:**

The canonical LLM call is:
```
llm.completion(prompt)
```

RLMs propose:
```
rlm.completion(prompt)
```
where `prompt` becomes a variable inside a sandboxed REPL, and the LM writes programs to:
- peek/search/slice/decompose the prompt
- recursively call sub-agents on only the needed snippets
- keep sub-agent outputs out of the parent's context by default (they come back as REPL variables/symbols, not appended text)

Source: The ChatGPT response cites the arXiv paper (2512.24601) and the fast-rlm GitHub repo. The anti-context-bloat rule is explicitly attributed to fast-rlm's design.

**Confidence:** HIGH — directly stated in source, attributed to both paper and repo.

**Implication for Entif:** Changes the API boundary for long-context operations; would replace lossy context-feeding with a programmatic mounting interface.

## Finding: RLM-001-M

**Topic:** Context rot is empirically confirmed; RLMs solve it by refusing neural attention over large token counts

**Raw findings:**

"Context rot research and practitioner writeups converge on the same empirical truth: as irrelevant tokens increase, retrieval accuracy and reasoning fidelity degrade in non-obvious ways." (attributed to research.trychroma.com/context-rot)

RLMs solve this not by attending over 10M tokens at once, but by:
- The "long prompt" becomes an external memory substrate
- The model uses programmatic attention (search + decomposition + targeted subcalls)
- The final answer is assembled from a controlled set of evidence snippets, not from a giant soup

Source: The response explicitly references the arXiv paper for the RLM architectural approach and the Chroma research site for context rot empirical evidence.

**Confidence:** MEDIUM — context rot characterization is attributed to a cited source; the RLM solution framing is attributed to the paper. Not a direct quote from either primary source.

**Implication for Entif:** Validates the problem space; suggests Rosetta as the external memory substrate.

## Finding: RLM-001-H

**Topic:** fast-rlm implementation details

**Raw findings:**

`avbiswas/fast-rlm` is a minimal implementation of the RLM paper, built around a REPL + recursion loop, with:
- Recursive decomposition (spawn sub-agents)
- REPL-based reasoning (execute Python iteratively)
- Budget controls (depth/calls/dollar spend caps)
- OpenAI-compatible provider routing (defaulting to OpenRouter via `RLM_MODEL_BASE_URL`)
- Structured JSONL logging + a TUI log viewer

The response characterizes fast-rlm as already shaped like an "Entif-ish" component: budgets + receipts-style logs + replaceable model backends.

**Confidence:** HIGH — directly describes repo contents and API design.

**Implication for Entif:** Direct template for ContextRuntime component; JSONL logging aligns with receipt-first design.

## Finding: RLM-001-M

**Topic:** Rosetta/Tiles as persistence model for RLM recursion

**Raw findings:**

"If Rosetta is your content-addressed truth spine, then every RLM operation should emit:
- `Observation` tiles: the snippet spans pulled from the mounted corpus
- `Action/ToolCall` tiles: REPL program steps + subcall metadata
- `Derived` tiles: intermediate summaries, indexes, maps, diffs
- `Evaluation` tiles: verifier scores (did this step actually support the claim?)"

This gives reproducibility: the RLM "answer" becomes a replayable DAG, not a mystical blob.

**Confidence:** MEDIUM — this is an explicit mapping suggestion; it synthesizes RLM operations onto existing Entif primitives (Rosetta, tiles) without direct prior art in the source. The tile types listed are proposed extensions.

**Implication for Entif:** Concrete proposal for how RLM outputs become first-class Rosetta citizens.

## Finding: RLM-001-H

**Topic:** RLM requires sandboxing and governance; belongs in analysis plane

**Raw findings:**

"RLM is code execution, which means:
- You must sandbox it (no ambient network, constrained filesystem, resource quotas)

In Entif terms: RLM belongs in the "analysis plane," and any "actuation plane" action requires policy gates + explicit approval.

**Confidence:** HIGH — explicitly attributed framing. The plane separation (analysis vs actuation) is described as an Entif framing.

**Implication for Entif:** Strong architectural constraint: RLM must be sandboxed and governed before integration.
