This document is a meta-design artifact: a multi-turn ChatGPT co-design session that iteratively refines a Pro-tier Deep Research prompt for the Rosetta Pasigraphy Protocol and Entif MVP. It progressively sharpens prompt requirements from (1) architecture-heavy, through (2) repo-scaffold-heavy TDD-first, to (3) a final consolidated prompt that also adds TypeScript/Nx-first stack commitment, file-level Rosetta traceability headers, and explicit solo-builder realism constraints. ## Conceptual Claims

- A single Pro-tier Deep Research prompt can function as a "scaffold forge" if it is correctly structured: forcing artifact-first output, TDD-first methodology, and backlog-as-failing-tests leaves behind maximum usable residue when the run exhausts its token budget
- Rosetta v3.0.0 should be treated as the stable semantic spine, not decorative metadata — all other systems attach to it
- The most important structural upgrade from iteration 1 to iteration 2 is the shift from "architecture-first" to "scaffold-first, test-first, acceptance-first" — making the DR run produce tests and stubs rather than prose descriptions of what those things should be
- The Nx monorepo decision is justified by shared contracts, shared generators, shared ledger semantics, MCP tool packages, cross-cutting CI targets, and Nx's affected-project computation model
- The TypeScript-first / Python-secondary stack decision resolves ambiguity that would otherwise cause the implementation to "split the baby" between languages
- The file-level Rosetta traceability header is specifically required for files implementing protocol semantics, policy logic, canonicalization, provenance, guard behavior, receipt logic, pack/versioning rules, or rights-sensitive retrieval — this is an audit and maintainability requirement, not decoration
- The "known red tests allowed" policy is distinct from the "must be green before tag" policy — in-progress failing tests are tracked but not blocking; only release-tagged builds require a fully green suite
- ACP/ACPX protocols are useful as edge adapters but are explicitly rejected as the constitutional center — Rosetta + Guard + Tripwire + receipts constitute the constitutional center, not ACP

## Contradictions Or Supersession

The final consolidated prompt (turn 4 / "FINAL REFINEMENTS" section) supersedes it by incorporating the repo-scaffold-heavy and stack-committed refinements. - **This document's file-header convention supersedes any prior ad hoc documentation approach:** Prior project documentation had no mandatory file-level traceability header requirement. This document introduces that requirement for protocol-sensitive files and should be treated as the new documentation standard for those file types.

This document explicitly isolates Python behind clear workspace boundaries and typed contracts and rules out splitting the core spine ambiguously across both languages.

## Open Questions

- **Q1:** The `cas://` URI scheme used in receipt examples uses `sha256:` content hashes, but does not specify the full hash algorithm profile (e.g., multihash format with varint length prefix). Should Rosetta adopt multihash ( IPLD format) or use plain SHA-256 hex strings? This affects CID compatibility with IPFS and other content-addressed systems.
- **Q2:** The Nx Cloud integration is referenced as a requirement but no specific Nx Cloud workspace ID or billing/account setup is documented. Is Nx Cloud available in the current project context, or is this a future requirement?
- **Q3:** The scaffold uses SQLite as a receipt ledger sink (under `receipt-ledger/src/sinks/sqlite.ts`), but the NOT LAME PRD specifies PostgreSQL as the canonical registry with SQLite only as a local shadow. What is the migration path from SQLite (MVP) to PostgreSQL (production)? Is Bootstrap currently using SQLite, and does this scaffold conflict with the NOT LAME PostgreSQL requirement?
- **Q4:** The Python `eval-harness` and `embedding-lab` packages are stubbed in the scaffold but no specific eval harness design or embedding strategy is defined. Should these be deferred to a separate Python-focused sprint, or are there immediate eval requirements that must be addressed in the MVP?

- **Q6:** The final prompt was designed for a Pro-tier Deep Research run and produced the scaffold-forge output in a single response. Would running this exact prompt produce the same quality of output, or does the iterative refinement in the ChatGPT session (3 turns) add value that a single-shot run cannot replicate?
