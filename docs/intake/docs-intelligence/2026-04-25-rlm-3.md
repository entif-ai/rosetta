## Finding: RLM-003-H

**Topic:** RLM anti-context-rot mechanism: prompt-as-environment, not prompt-as-input

**Raw findings:**

The RLM paradigm shifts context management from "feed context into transformer" to "treat context as an external object the model programs against." The full prompt `P` lives as a variable in a persistent REPL environment `E`. The base LM only sees the "control transcript" (metadata + code + bounded stdout). The model selectively inspects `P` via code rather than via attention over all tokens.

This is described as the antidote to "context rot" — quality degrading steeply as prompts get longer. The paper calls this out explicitly: long prompts are "part of an external environment," and the model can **examine, decompose, and recursively call itself over snippets** of that prompt.

Source: Response section 1A, citing the arXiv paper 2512.24601v2.

**Confidence:** HIGH — explicit architectural claim from the paper, directly quoted in the response.

**Implication for Entif:** Rosetta's external memory substrate (Bootstrap → Text-Core) aligns with this pattern. The "prompt" in Entif's case is the session/task/artifact state. The model should program against it, not attend over it.

## Finding: RLM-003-H

**Topic:** Recursive subcalling: symbolic buffers, not paste-back text; 10-59% gains on dense benchmarks

**Raw findings:**

Inside the REPL, the root model writes code that programmatically invokes sub-LLM calls and iterates, rather than narrating everything autoregressively. Critically: "sub-agent responses are not automatically loaded into the parent context; they come back as symbols/variables inside the parent REPL." This "return as symbols, not paste-back text" is identified as a core anti-rot primitive.

The paper reports cases where recursive sub-calling is necessary (e.g., line-by-line transformations through recursive calls), with gains of **10%–59% vs a no-subcall ablation** on information-dense benchmarks.

Source: Response section 1B, citing the arXiv paper 2512.24601v2 and fast-rlm docs.

**Confidence:** HIGH — empirical results explicitly attributed to the paper; fast-rlm's variable-return mechanic directly described.

**Implication for Entif:** Every sub-agent response should return a handle (tile_cid, receipt_id, observation_handle) rather than raw text that gets concatenated into the parent context. This is the programmatic equivalent of Entif's receipt-first artifact lifecycle.

## Finding: RLM-003-H

**Topic:** RLMs scale to 10M+ token regime; cost distribution has fat tail

**Raw findings:**

RLMs explicitly claim they can scale to the **10M+ token regime**, outperforming base models and common scaffolds by up to **2×** while keeping comparable or cheaper average costs. However, the cost distribution has a fat tail: median can be better, but outliers can be far more expensive due to long trajectories.

The paper's "engineering notes" also caution that `llm_query` is expensive and users should **batch aggressively** rather than making lots of tiny subcalls. Their implementation used blocking/sequential calls and was slow; they call out async subcalls + sandboxed REPLs as a path to reduce runtime and cost.

Source: Response section 1C and 1D, citing the paper's own engineering notes.

**Confidence:** HIGH — explicitly attributed to the paper's empirical claims and engineering notes.

**Implication for Entif:** Long-context Entif sessions should use the RLM pattern, not simple context extension. Budget controls + async subcalls are non-negotiable for cost predictability. The fat tail risk must be mitigated by Guard-enforced hard stops.

**Raw findings:**

The three primitive operations (mount, run, inspect) map to Entif's existing mount → execute → observe lifecycle.

## Finding: RLM-003-H

**Topic:** Cognitive Tiles as RLM symbolic buffers (content-addressed handles replacing REPL variables)

**Raw findings:**

The RLM paper uses variables as symbolic buffers. Entif should use **content-addressed tiles** instead. The response proposes that instead of returning a raw string from a sub-agent, return:
- `tile_cid` for an Observation / Derived artifact
- `run_id` / `receipt_id`

This turns an RLM trajectory into a reproducible "proof-carrying" computation graph rather than "trust me bro, the agent read it."

The response notes that the existing tile framework already specifies content-addressed, immutable Merkle-DAG objects with provenance/proofs (from the Cognitive Tiles spec).

Source: Response section 3B, citing the Cognitive Tiles and Swarm Gnosis spec.

**Confidence:** HIGH — explicit mapping of RLM symbolic buffers to existing Entif/Cognitive Tile primitives.

**Implication for Entif:** The tile framework is the correct primitive for RLM handle return values. This is not a new capability — it's using existing capabilities (Cognitive Tiles, Merkle-DAG provenance) in a new integration pattern. The receipt schema already supports this.

## Finding: RLM-003-H

**Topic:** Async subcalls for RLM performance: producer-consumer pattern

**Raw findings:**

The paper is explicit: naive RLMs are slow when subcalls are blocking/sequential. The paper's own engineering notes suggest async subcalls + sandboxed REPLs as future improvements.

Entif can do better than the paper by designing:
- REPL requests subcalls by enqueuing jobs (with budgets + policy tokens)
- Workers execute independently and return results as tiles
- Root REPL polls/awaits completion and keeps going

This gives "procedural attention" without turning runtime into a single-threaded hostage situation.

Source: Response section 3D, citing the paper's engineering notes and the Entif 2.0 action plans.

**Confidence:** HIGH — explicit performance optimization recommendation, directly derived from the paper's own stated limitation.

**Implication for Entif:** The worker queue pattern for subcalls is the correct implementation approach. This aligns with Entif's async-first design elsewhere in the system. The job enqueue → tile return → poll/await flow maps to existing worker patterns.
