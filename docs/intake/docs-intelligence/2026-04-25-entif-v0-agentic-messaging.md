## Summary

An inter-agent communications protocol for Entif v0: signed envelope format (ed25519), typed message schemas (data plane vs control plane), a mailroom ingest pipeline with quarantine-first staging, GuardLayer policy enforcement, and a 5-step minimal implementation sequence. The spec references Rosetta objects (receipt, incident, iam.decision) but was likely authored in a parallel design cycle — minimal integration with NOT LAME PRD, Text-Core MVP, or the three-rung build staircase. No JSON schemas, no diagrams, no defined storage schemas for quarantine→canonical transition.

## Goals And Intent

- Secure, typed, auditable message exchange across heterogeneous agent runtimes and nodes
- No untrusted text can become executable intent
- All downstream memory writes derive from verified canonical Rosetta objects
- Support "replaceable execution substrates" while preserving a single coherent truth/audit spine

## Components And Technologies

- ed25519 (digital signatures)
- sha256 (payload integrity)
- UUID (message identification)
- mTLS (transport authentication)
- VPN / WireGuard / Tailscale (network tunneling)
- nonce + expires_at (replay protection)
- Rosetta tiles and tapestries (canonical object model)
- GraphRAG / vector store / SQL (downstream persistence)
- GuardLayer (RBAC/ABAC policy enforcement)
- INCIDENT_ENVELOPE (typed security event reporting)

## Conceptual Claims

- Inter-agent messages can be cleanly separated into data plane (no privileged side effects) and control plane (privileged actions gated by Guard)
- Signed envelopes provide integrity and authentication without requiring full payload encryption
- Quarantine-raw + canonicalize-later pattern prevents malformed or malicious messages from polluting downstream stores
- Replaceable execution substrates are compatible with a stable audit spine if the audit spine is message-based and Rosetta-object-anchored
- Prompt injection text can be safely contained at the data plane without semantic understanding at the perimeter

## Dependencies And Sequencing

- Depends on: Rosetta object definitions (receipt, incident, tile, tapestry), Guard/iam.decision API, NOT LAME PRD write-admission gate
- Blocked by: JSON schema definitions for message types and envelope, nonce store implementation, mTLS certificate provisioning design
- Sequencing: Section 11 minimal implementation order (signed envelopes first, semantic interpretation last)

## Contradictions Or Supersession

- **Semantic understanding as security control (Non-Goal vs. Threat Assumption):** The spec explicitly excludes semantic understanding from the security perimeter (Section 1 Non-Goals) but simultaneously assumes prompt-injection text will ride inside payload (Section 2.2 Threat Assumptions) — these are in tension: if prompt injection is a threat but semantic understanding is not used as a control, the threat is unmitigated by design
- **This spec predates NOT LAME PRD by ~2 months:** Likely authored as a parallel design track; needs integration with current Rosetta architecture before adoption

## Open Questions

- What is the precise scope of the mailroom — inter-agent bus only, or general Rosetta ingress boundary for all message types (including skillpack imports, human messages, tool calls)?

- Domain_ref format: is the ABAC label set open-ended (arbitrary strings) or a controlled vocabulary? Who governs the classification taxonomy?
- Quarantine ciphertext scope: are envelope headers (sender, routing_key, domain_ref) encrypted or only integrity-checked? What encryption algorithm if any?
- Routing_key collision: if two messages with the same routing_key arrive simultaneously from different senders, what is the collision handling behavior?
- How does the Section 11 implementation sequence interact with the three-rung build staircase (Bootstrap → Text-Core MVP → Alpha RC)? Which rung does this land in?
