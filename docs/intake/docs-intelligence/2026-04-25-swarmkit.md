## Extraction

### 1. Overview and Positioning

SwarmKit is a toolkit for orchestrating distributed systems at any scale, built in Go. It is the foundational engine that became Docker Swarm Mode in Docker Engine 1.12. The project provides primitives for node discovery, Raft-based consensus, task scheduling, and more — without external database dependencies (the Raft log IS the state store).

Key differentiator: it ships its own Raft-based strongly-consistent state store embedded in manager nodes, making it operationally simple and eliminating external dependencies like etcd or ZooKeeper.

### 2. Architecture

#### Node Model
- Nodes are either **Worker** or **Manager** roles.
- **Worker Nodes**: run Tasks using an Executor (default: Docker Container Executor, swappable).
- **Manager Nodes**: accept user specifications, reconcile desired state vs. actual cluster state.
- Roles are dynamically changeable (promote/demote) at runtime via API/CLI.

#### Task → Service Hierarchy
- **Tasks** are the atomic unit of work.
- **Services** are the higher-level abstraction that declares desired state for a group of Tasks (e.g., replica count, update behavior).
- Two service types shipped out of the box:
  - **Replicated Services**: scale to N desired replicas.
  - **Global Services**: run one task on every available node in the cluster.

#### Swarm Structure
- A **Swarm** is a cluster of machines running SwarmKit.
- Manager nodes form a Raft quorum; no external consensus system needed.
- In-memory reads are extremely fast; all scheduling decisions flow through the replicated state store.

### 3. Core Design Patterns

#### 3.1 Desired State Reconciliation (DSR)
The orchestrator continuously compares desired state against current cluster state and reconciles differences. Example: node failure → tasks rescheduled onto different node. This is a closed-loop control system with event-driven triggers.

#### 3.2 Raft Consensus
- **No single point of failure**: coordination uses the Raft Consensus Algorithm.
- Manager nodes maintain a strongly consistent, replicated (Raft-based), in-memory view of the cluster state.
- This allows fast scheduling decisions while tolerating failures.
- Note: SwarmKit predates the etcd-based Docker Swarm mode; its Raft is embedded.

#### 3.3 Mutual TLS + CA
- All node-to-node communication is mutual TLS.
- Swarm managers act as a **Root Certificate Authority**, issuing certificates to new nodes.
- **Token-based join**: cryptographic token defines the joining node's role. Tokens can be rotated without affecting already-joined nodes.
- **Certificate rotation**: TLS certs are rotated and reloaded transparently on every node (default: 3 months, min: 30 minutes).

#### 3.4 Executor Pattern
- Worker nodes use an **Executor** to run Tasks.
- Default executor: **Docker Container Executor**.
- Executor interface is swappable — allows custom execution backends (e.g., to run non-Docker workloads).

### 4. Orchestration Features

#### 4.1 Service Update Strategy
- Updates are reconciled by ensuring all tasks use new settings.
- Default: **lockstep** (all tasks updated simultaneously).
- Configurable via knobs:
  - **Parallelism**: max concurrent updates.
  - **Delay**: minimum wait between updates. Sequence: shut down old task → bring up new → wait for RUNNING → wait additional delay → proceed to next task.
- Update options are sticky: if an update command omits them, the last set of options is reused.

#### 4.2 Restart Policies
- Orchestration layer monitors tasks and reacts to failures.
- Configurable: **conditions**, **delays**, **limits** (max restarts in a time window).
- SwarmKit can restart a task on a different machine.
- **Faulty node drainage**: nodes gradually lose tasks via restart re-scheduling.

#### 4.3 Task History
- Default task history entries: 5 (configurable per cluster).
- Used for job/status tracking and reconciliation lookback.

### 5. Scheduling

#### 5.1 Resource Awareness
- Scheduler is aware of resources available on nodes.
- Places tasks according to resource constraints.

#### 5.2 Constraint Expressions
- Operators limit which nodes a task can be scheduled on.
- Constraint matching is **AND** (all expressions must be satisfied).
- Available node attributes:

| Node Attribute | Matches | Example |
|---|---|---|
| `node.id` | Node's ID | `node.id == 2ivku8v2gvtg4` |
| `node.hostname` | Node's hostname | `node.hostname != node-2` |
| `node.ip` | Node's IP address | `node.ip != 172.19.17.0/24` |
| `node.role` | manager or worker role | `node.role == manager` |
| `node.platform.os` | Operating system | `node.platform.os == linux` |
| `node.platform.arch` | Architecture | `node.platform.arch == x86_64` |
| `node.labels` | Admin-added labels | `node.labels.security == high` |
| `engine.labels` | Docker Engine labels | `engine.labels.operatingsystem == ubuntu 14.04` |

- **node.labels**: added by cluster admins for operational purposes (e.g., security compliance labels).
- **engine.labels**: collected from Docker Engine (OS, drivers, etc.).

#### 5.3 Spread Strategy
- Default and only strategy shipped: attempts to schedule tasks on the **least loaded** nodes, subject to constraints and resource requirements.

### 6. Cluster Management

#### 6.1 State Store
- Manager nodes maintain a strongly consistent, replicated, in-memory state view.
- Raft-based replication; all reads are fast in-memory operations.

#### 6.2 Topology Management
- Node roles (Worker/Manager) can be dynamically changed via API/CLI.

#### 6.3 Node Availability
- **Active**: normal scheduling.
- **Paused**: no new tasks scheduled; existing tasks continue running.
- **Drained**: no new tasks scheduled; existing tasks are re-scheduled elsewhere (for maintenance).

### 7. Security Model

- **Mutual TLS**: all inter-node communication authenticated and encrypted.
- **CA Role**: managers act as root CA, issuing certs to joining nodes.
- **Token-based Admission**: join tokens encode role; rotatable without cluster disruption.
- **Automated Certificate Rotation**: certificates rotated and reloaded transparently; configurable rotation frequency.

### 8. Build and Test

- **Requirements**: Go 1.6+, working golang environment, Protobuf 3.x+ (for `make generate`).
- **Binaries built**: `swarmd` (daemon), `swarmctl` (CLI control tool).
- **Test setup**: `make setup` then `make all`.
- **Socket-based control API**: managers listen on a Unix socket (`--listen-control-api`) for `swarmctl` CLI access. `SWARM_SOCKET` env var points to this socket.

### 9. Command Examples (from README)

#### Node Join
- Workers: `swarmd -d /tmp/node-N --hostname node-N --join-addr <addr> --join-token <Worker Token>`
- Managers: additionally require `--listen-control-api` and `--listen-remote-api`.

#### Cluster Inspect (to get join tokens)
- `swarmctl cluster inspect default` — returns join tokens and cluster config.

#### Service Lifecycle
- Create: `swarmctl service create --name redis --image redis:3.0.5`
- Scale: `swarmctl service update redis --replicas 6`
- Update with parallelism/delay: `swarmctl service update redis --image redis:3.0.7 --update-parallelism 2 --update-delay 10s`

#### Node Maintenance
- `swarmctl node drain node-1` — re-schedules all tasks off node-1.

## Concepts Learned

- **Raft Consensus Algorithm** — distributed consensus without single point of failure; embedded in SwarmKit managers
- **Desired State Reconciliation (DSR)** — closed-loop control pattern: diff desired vs actual → reconcile
- **Mutual TLS / mTLS** — mutual authentication + encryption between all nodes; CA-issued certificates
- **Token-based Admission** — cryptographic join tokens encode role; rotatable without cluster disruption
- **Executor Pattern** — swappable runtime backend for Tasks (default: Docker Container Executor)
- **Spread Strategy** — scheduling heuristic that distributes load to least-loaded feasible nodes
- **Node Availability Model** — Active/Paused/Drained trinary node availability for maintenance workflows
- **Service Types** — Replicated (N replicas) vs Global (one per node); both shipped out of the box
- **Update Parallelism + Delay** — configurable rolling update with parallelism knob and inter-update delay
- **Restart Policies** — condition/delay/limit triptych for task recovery with backoff
- **In-memory fast reads + Raft-writelog** — state store architecture: replicated write log + in-memory reads
- **Unix socket control API** — manager CLI communication via Unix domain socket (SWARM_SOCKET env var)
- **Task History Entries** — configurable history window for job tracking and reconciliation lookback
- **Constraint Expressions** — AND-matching node attribute selectors for task placement
- **Node Labels** — admin-defined (`node.labels`) vs engine-reported (`engine.labels`) node attributes

## Issue Candidates

1. **Investigate whether Rosetta's slot reconciliation loop should adopt an explicit "desired state diff → action" architecture** similar to SwarmKit's DSR model. Currently Rosetta reconciles slots based on declared capabilities, but the model is more implicit. An explicit DSR pattern could make the orchestration loop more observable, testable, and debuggable.
2. **Consider adopting a swappable Executor interface for Rosetta CTs** so that execution backends (Docker, containerd, bare-process, etc.) can be plugged in without modifying core orchestration logic. This aligns with SwarmKit's executor pattern.
3. **Adopt SwarmKit's restart policy model (condition/delay/limit)** for Rosetta CT lifecycle management. The current model has fewer configurable knobs; adding the full triptych would improve fault-tolerance configurability.
4. **Design a token-based auth + certificate rotation system for Rosetta inter-node communication** modeled on SwarmKit's mTLS + CA architecture. Rosetta currently uses tokens but may lack the automated certificate lifecycle management (transparent rotation, configurable interval, CA role delegation).
5. **Add a Global CT pattern to Rosetta** analogous to SwarmKit's Global Services — one CT instance on every eligible node, constrained by node labels/platform attributes. This would be valuable for cluster-wide services (logging agents, monitoring sidecars, etc.).
6. **Investigate the in-memory + Raft log state store pattern** for Rosetta's cluster state. SwarmKit shows this is viable without etcd/ZooKeeper; Rosetta could evaluate whether its cluster state management needs similar tradeoffs.
7. **Consider implementing a `node availability` model (Active/Paused/Drained)** for Rosetta nodes to support graceful maintenance windows without disrupting running capabilities.
