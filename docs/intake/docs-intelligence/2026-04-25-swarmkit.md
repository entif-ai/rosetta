## Summary

SwarmKit is a Raft-based distributed systems toolkit providing node discovery, task scheduling, service orchestration, and mutual TLS security. It underpins Docker Swarm and is architecturally notable for its self-contained design (no external database), in-memory strongly consistent state store, and configurable rolling updates. For Rosetta's intake intelligence layer, it offers an instructive reference architecture for distributed state, node roles, desired-state reconciliation, and security token flows — patterns potentially relevant to Entif's memory and decisioning subsystems. Its age and stagnation are a caution against direct dependency.

## Components And Technologies

- **SwarmKit**: Core orchestration toolkit (Go-based, moby/swarmkit)
- **Raft Consensus Algorithm**: Distributed leader election and state replication
- **swarmd**: Node daemon (manages both worker and manager roles)
- **swarmctl**: CLI control tool for cluster interaction via Unix socket
- **Mutual TLS (mTLS)**: Node authentication and encrypted inter-node communication
- **Root CA (Manager)**: Managers issue certificates to joining nodes
- **Cryptographic Join Tokens**: Role-specific tokens for node admission
- **Docker Container Executor**: Default task executor (pluggable)
- **In-memory State Store**: Raft-replicated, strongly consistent, no external DB
- **Unix Domain Socket IPC**: swarmctl communicates with swarmd via `SWARM_SOCKET`
- **Desired State Reconciliation Loop**: Core scheduling and fault-recovery mechanism
- **Spread Scheduling Strategy**: Default (only) scheduling strategy — least-loaded node preference
- **Protobuf 3.x**: Serialization format for inter-node communication

---

## Conceptual Claims

- SwarmKit achieves fault-tolerance through Raft-based leader election without external dependencies (no external DB, no ZooKeeper, no etcd)
- Security is intrinsic and automatic: mutual TLS + certificate rotation means all node communication is encrypted and authenticated by default
- Operational simplicity is a first-class design goal: token-based join means no pre-shared secrets; manager Election does not require manual configuration of peers
- The reconciliation loop pattern (compare desired vs actual state, reconcile continuously) is the fundamental scheduling primitive
- Node roles (Worker/Manager) and availability (Active/Paused/Drained) are dynamically mutable without node restart
- The pluggable executor architecture enables heterogeneous workloads beyond containers (theoretically)
- Certificate validity duration is configurable with a floor of 30 minutes, balancing security and operational convenience

## Dependencies And Sequencing

- SwarmKit is a standalone Go project; no external service dependencies for core operation
- Build tooling requires Go 1.6+ and Protobuf 3.x — both easily satisfied in 2026 environments (though Go 1.6 is ancient)
- The SwarmKit state store is self-contained (in-memory Raft); no external database dependency
- Docker Container Executor depends on a Docker Engine on each node (implicit runtime dependency)
- Node join requires token and address of an existing manager — bootstrap sequence matters (first manager must be initialized before others can join)

## Contradictions Or Supersession

- **Supersession risk**: SwarmKit is the core of Docker Swarm mode, which itself has been largely superseded by Kubernetes in enterprise production environments. This document likely describes architecture that is no longer actively developed. Engineering teams should not plan new projects around SwarmKit as a primary dependency.
- **Go version mismatch**: Document specifies Go 1.6 as minimum (2016 era). Modern Go projects should target Go 1.21+; this requirement is dated and likely prevents compilation on current toolchains without modification.
- **Single scheduling strategy**: Only `spread` strategy shipped — no pluggable scheduling algorithms. Constraint-based filtering is the primary extensibility mechanism, which is limited compared to Kubernetes schedulers.
- **No external state store**: While simplifies deployment, in-memory Raft limits state store durability compared to etcd-backed solutions. Data loss risk on full cluster shutdown.
