## Summary

This document is a technical companion to Entif 2.0 Comprehensive Action Plans, covering five areas: (1) Guard Layer and real-time governance, (2) Self-monitoring threat intelligence, (3) Genesis Protocol and immutable authority hierarchy, (4) Decentralization with blockchain/tokenomics, and (5) Zero-trust node design with local autonomy. It is a substantial 2025-era design document that overlaps significantly with NOT LAME PRD's sovereign-kernel and write-admission-gate concepts, but uses different terminology (Majordomo, Genesis Protocol) that is not aligned with Rosetta's current vocabulary. Many features described here (blockchain ledger, HSM multisig, ZKP-based validation) are aspirational far-future work, not near-term implementation targets.

## Goals And Intent

- Provide detailed implementation blueprints for the five named areas as a companion to Comprehensive Action Plans
- Anchor agent governance in cryptographic, human-controlled authority rather than implicit trust
- Enable local node autonomy without compromising ecosystem integrity

## Components And Technologies

- **Open Policy Agent (OPA) + Rego** — policy-as-code engine for allowlist/denylist enforcement
- **SPIFFE/SPIRE** — workload identity framework for just-in-time permissions
- **Firecracker / gVisor** — lightweight VM sandboxing for high-risk operations
- **Cryptographic hash chain / blockchain** — tamper-evident immutable audit log (conflicts with NOT LAME's PostgreSQL canonical registry)
- **NIST NVD / CVE feeds** — threat intelligence data sources
- **RAG + vector DB (Milvus/Pinecone)** — LLM-augmented threat analysis
- **SBOM (Software Bill of Materials)** — component inventory for CVE cross-referencing
- **Genesis keypair (Ed25519)** — root of trust, public hardcoded, private multi-sig controlled
- **HSM (Hardware Security Module)** — air-gapped key storage for Genesis signing ceremonies
- **Multi-sig (5-of-7 Gnosis Safe or custom)** — Genesis-level change approval
- **Permissioned blockchain / Ethereum sidechain / Cosmos** — audit trail and governance transactions
- **Proof-of-Stake consensus** — validator node incentive model
- **ZK-SNARK / ZK proofs** — computation verification (conflicts with CT-006 "not near-term" finding)
- **Docker/VM signed images** — node software distribution with release key signatures
- **TPM / Intel SGX / ARM TrustZone** — hardware attestation for node integrity
- **Ed25519 node keypair** — per-node cryptographic identity
- **Linux namespaces + seccomp/BPF** — node internal compartmentalization
- **mTLS + schema validation** — strict API contracts between nodes

## Conceptual Claims

1. **Guard Layer as universal interceptor**: All agentic operations must pass through the Guard Layer regardless of origin — even Majordomo (the central orchestrator) is subject to Guard supervision. This is a stricter posture than the current "parse-only default until guard token" model in Authority Stack.
2. **Policy-as-code enables auditability**: Encoding governance rules as Rego policies makes the Guard's decision logic auditable, versioned, and testable — analogous to how Rosetta encodes receipt rules.
3. **Immutability is structural, not ceremonial**: Audit logs and Genesis Protocol are immutable by cryptographic construction (hash chain, HSM), not by organizational promise.
4. **Genesis Protocol is the constitutional ceiling**: No agentic subsystem can override or persist changes to the Genesis Protocol; even an "advanced AI that rewrites some code" cannot propagate that change because it lacks the multisig signature.
5. **Decentralization requires economic incentives**: Without tokenomics (PoS, slashing, reputation), there is no economic deterrent for node operators to behave correctly — trust alone is insufficient.
6. **Zero-trust means verification without revelation**: Nodes can validate each other's behavior via ZK proofs or attestation quotes without seeing each other's data or internal architecture — privacy-preserving verification.
7. **Threat intelligence is separate from agent governance**: The threat monitor watches the external world (CVEs, exploits); the Guard watches internal agent behavior. Conflating them creates scope creep and blurred responsibility boundaries.

## Dependencies And Sequencing

- **Guard Layer implementation** depends on: sovereign-kernel design (NOT LAME), write-admission-gate spec (NOT LAME), OPA integration (future), sandbox technology selection (future)
- **Genesis Protocol (multisig + HSM)** depends on: separate infrastructure project for HSM hardware, key ceremony design, physical security; no current path to implementation
- **Blockchain audit trail** is in direct conflict with NOT LAME's PostgreSQL canonical registry; must be resolved before either is implemented
- **ZKP node validation** conflicts with CT-006; CT-006 takes precedence — ZKP deferred to post-MVP phases
- **Threat Monitor (CVE/NVD)** is a separate workstream from agent governance; can be independent future project, not blocking for Text-Core MVP
- **Zero-trust node packaging (TPM/SGX/signed images)** is aspirational long-horizon infrastructure; no current implementation path
- **Emergency halt mechanism** should be captured as sovereign-kernel requirement and is the one near-term actionable item from this document

## Contradictions Or Supersession

- **Blockchain vs PostgreSQL**: Document proposes blockchain ledger for audit trail; NOT LAME specifies PostgreSQL as canonical registry. These are incompatible for the same data. Resolution: NOT LAME takes precedence for near-term; blockchain is future option.
- **ZKP timing**: Document proposes ZKP for near-term node validation; CT-006 from prior extraction explicitly classifies ZK as not near-term viable (proof generation too expensive). CT-006 takes precedence.
- **Guard Layer vs write-admission-gate**: These describe the same conceptual function (policy enforcement on agent actions) with different terminology and structural detail. No contradiction — Guard Layer spec should inform write-admission-gate implementation.
- **Terminology gap**: Document predates Rosetta's current vocabulary (Majordomo vs sovereign kernel, Genesis Protocol vs Doctrine, blockchain vs PostgreSQL). All references to "Majordomo" should be read as "sovereign kernel (or its sub-components)" in current Rosetta context.
