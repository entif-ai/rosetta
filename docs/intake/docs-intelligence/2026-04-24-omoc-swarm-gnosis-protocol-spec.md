## Summary
This RFC synthesizes the OMOC routing doctrine, Swarm Gnosis federation layer, MR TECH LEAD compute ideology, and existing Rosetta/Entif memory architecture into a unified six-layer metacognitive substrate. Its central contribution is establishing OMOC as a concept-simplex routing primitive that replaces static expert personas, formalizing Swarm Gnosis as a staged federated exchange for signed cognitive tiles and tapestries, and sharpening MR TECH LEAD as a compute ideology that must remain strictly subordinate to Rosetta's semantic constitution. It also defines an explicit 8-tack build order with acceptance gates, proposes eight companion schema and seven ROCK-family companion specs, and enumerates eight genuinely open research questions that should remain unresolved at this stage.

## Goals And Intent
- Consolidate the strongest existing artifacts (Rosetta v3, ROCK-31XX, Entif memory doctrine, MR TECH LEAD, taxonomy work) into one coherent architectural thesis and engineering doctrine
- Keep Rosetta v3 as the invariant semantic and provenance spine without core redefinition
- Establish OMOC as the routing law (conceptual composition, not expert identity)
- Formalize Swarm Gnosis as the distributed exchange layer for verified cognitive artifacts
- Integrate MR TECH LEAD without letting compute innovations bloat the semantic constitution
- Define buildable execution order (epistemic sequencing → 8-tack build with acceptance gates)

## Conceptual Claims

1. **OMOC is concept-native, not expert-native.** Routing currency is conceptual structure derived from task decomposition, not static expert persona selection. The system asks "what conceptual basis set is present?" not "which expert do I wake up?"
2. **Six-layer stack is the correct integration model.** A/B = constitutional, C/D = cognitive, E = operational, F = federative/infrastructural. Each group has distinct failure modes, governance needs, and build timelines.
3. **MR TECH LEAD is compute ideology, not semantic constitution.** Model-stack innovations each solve different dirty jobs and must not become a sacred block. Rosetta exists because tokenizers, embeddings, and latent states are not themselves a transparent semantic substrate — better internal routing does not replace this.
4. **Survivorship scoring is non-negotiable for niche work preservation.** Low local utility + high cross-context survivorship → demote cold tier, do NOT delete. This is the rule that stops OMOC from kneecapping future niche work.
5. **Rights-scoped retrieval is structural, not policy.** Retrieval scope enforcement at the boundary (not post-filter) is essential for privacy, multi-tenancy, selective disclosure, and swarm publication safety.
6. **Parse-only by default is a safety harness.** Ambient ingest must not produce side effects without explicit command mode + guard passage + receipts. This is load-bearing for zero-trust environments.
7. **ENGRAM + Rosetta is the strongest architectural pairing.** Static knowledge lookup via conditional memory + deterministic semantic keys avoids recomputation of stable truths. Rhymes directly with tiles, tapestries, slugs, compiled contexts, and semantic caches.
8. **Draft-and-Prune + Rosetta enables real semantic equivalence detection.** When candidate outputs are emitted as canonical semantic bundles (not just text), textual self-consistency checks are replaced by structural equivalence/contradiction detection.
9. **H-Neurons risk signal must attach to claim/receipt chain.** Isolated internal risk scores are not actionable. Only when attached to the claim/receipt chain and available to Guard/evaluators does risk become a policy factor.
10. **Federation must not begin with public swarm.** Staged layers: single-tenant → multi-agent → org-scoped → inter-org → public. Each layer requires stronger proof, rights, and abuse-handling than the last.
11. **Ontology school declaration prevents invisible ontology.** Every imported vocabulary must declare its school (philosophy/standards/taxonomy/linked-data/data-centric/object-oriented/hybrid). The worst ontology is not a wrong one; it is an invisible one.
12. **Common understanding is not raw embedding consensus.** Shared understanding emerges from canonical semantic objects, explicit mapping layers, typed ambiguity, stable references, and verifiable evidence chains — gauge blocks, not latent manifold hoping.
13. **Human delegates are valid swarm substrates.** HUMANS are valid delegate substrates with capability profile, domain signature, trust envelope. Automation purity is not a valid optimization target.
14. **Prompt-band stabilization enables OpenAI caching economically.** Stable long prefixes in higher bands enable exact repeated-prefix matching for prompt caching. This is a practical token-burn reducer.
15. **Eight open questions should stay open.** These are scoped unknowns, not weaknesses. Preserving them prevents premature false certainty blocking future learning.

- **Tack 5** (MR TECH LEAD reliability lane: Draft-and-Prune, H-Neurons, ENGRAM hooks) gates Tack 6 (simulation needs reliable route quality to base forecasts on)
- **Tack 6** (simulation-conditioned planning) gates Tack 7 (org-scoped federation needs working simulation before trust-boundary crossing)

- Receipt infrastructure (Tack 0) is a dependency for Guard, memory promotion/demotion, and federation

## Contradictions Or Supersession

- **Supersedes** the MR TECH LEAD holistic redesign doc (20260325) insofar as that doc could be read as suggesting MR TECH LEAD components could compete with or substitute for Rosetta semantics. This RFC makes explicit that MR TECH LEAD is compute ideology only.
- **Clarifies** the Entif memory doctrine (20260324) with respect to the six memory planes and their Rosetta-envelope representation requirement — the memory planes in Section 9.2 are more specific than the earlier expanded-plane architecture description.
- **Extends** ROCK-31XX by adding epistemic provenance modes (Section 7.3) and the claim/receipt/observation triple (Section 7.4) as schema extensions within the ROCK envelope, not core mutations.
- **Formalizes** informal OMOC concepts from prior synthesis documents into a concrete routing primitive with tranche schema, survivorship scoring formula, and delegate substrate types.
- **Does NOT contradict** any prior Rosetta core spec — explicitly refuses to redefine Rosetta core types or meaning-pipeline semantics (Section 1.3 Non-Goals).

## Open Questions
1. **OMOC routing determinism vs. learned:** How much of OMOC routing should be deterministic rule-based, and how much learned from concept-tranche outcome data? The doc acknowledges this is unresolved (Section 18, Q1). A lean first implementation likely favors deterministic; learned scoring may be a Tack 3+ or Tack 5+ refinement.
2. **Minimum semantic gauge-block set:** What is the minimum useful set of canonical semantic fixtures needed to calibrate cross-model semantic alignment? Without this, "common understanding" across model vendors remains hand-waving.
3. **Best early ontology packs:** Which ontology pack provides the best leverage early without devolving into ontology-religion drag? The facet-based classification approach (Section 6.1) mitigates this but does not fully resolve it.
4. **Slug hydration quality bottleneck:** How aggressively should symbolic and optical slugs be adopted before hydration quality becomes a bottleneck? This is a practical token-cost vs. semantic-fidelity tradeoff.
5. **Model-internal vs. external semantic structure timing:** When should the project prioritize model-internal innovation (AttnRes, Mamba corridors, etc.) versus investing in better external semantic structure (Rosetta envelopes, taxonomy, receipts)? The doc argues for the latter first but does not specify the trigger for switching.
6. **Public commons licensing model:** What licensing and governance model applies to Swarm Gnosis artifacts in the public commons? This is a legal and community-founding question that must not be deferred indefinitely if public commons is a stated goal.
7. **Human delegate priority:** Which classes of human delegates belong in the switchboard first? The doc acknowledges this is open but provides no priority heuristic.
8. **Selective disclosure for commercial multi-tenant use:** How should proof-carrying bundles and selective disclosure evolve to support commercial multi-tenant scenarios where privacy, competitive sensitivity, and auditability all apply simultaneously?
