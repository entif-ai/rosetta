## Summary

This document is the canonical Entif 2.0 system blueprint — a voice-driven cognitive command center for a single developer operating at "vibe speed." It specifies a layered architecture spanning ambient input ingestion, a voice-first orchestrator ("Ada"), a knowledge core (GraphRAG + Glyph Engine), advanced reasoning modules (TRM, ROMA, ReasoningBank), an evaluation/adaptation layer (ELIXIR + Coach), a safety system (Petri + Tripwire), a media & attention engine, and a Forge catalog of 15 specialized modules (MediaForge, SocialForge, ArticleForge, LyricsForge, WordForge, FileForge, ArchiveForge, MetadataForge, VersionForge, VizForge, AuthForge, BackupForge, UIForge, APIForge, and two supporting LLM plane Forges). It defines cross-cutting invariants (MCP everywhere, receipts-first, `entif://` URI scheme, Nx/Nx Cloud, ReasoningBank, TRM/ROMA, GraphRAG+Glyph, Petri/Tripwire), a 4-hour micro-tier development philosophy, and two parallel workstreams (Core Orchestration & Knowledge Loop; Media Engine & Attention Flywheel). Each Forge has purpose, architecture, interfaces, data models, integration points, truth fences, observability requirements, and implementation plans broken into milestones and ~4-hour tasks. The document also contains an extensive appendix that generated the Forge naming/catalog chapter from a ChatGPT conversation that originally left Forges unnamed.

## Goals And Intent

- Provide a complete, implementable architecture for Entif 2.0 as a voice-driven autonomous coding and content-creation system
- Establish the "receipts-first" evidence culture: every action produces a structured Receipt
- Enumerate all Forge modules with clear purpose, MCP interface, data models, integration points, and quality gates
- Define the 4-hour micro-tier delivery philosophy for incremental, compounding progress
- Align all modules to cross-cutting invariants: MCP at every boundary, Nx monorepo, `entif://` URI scheme, ReasoningBank, GraphRAG+Glyph, Petri/Tripwire, AuthForge, FileForge, ArchiveForge, VersionForge, VizForge
- Serve as the authoritative reference for all downstream implementation work and PRDs

## Conceptual Claims

- Voice-driven interaction with sub-second acknowledgment and end-to-end task completion within seconds for simple requests enables a developer to "operate at vibe speed"
- "One Truth, Many Views": all activities share a unified lifecycle (session → task → step → artifact → check → outcome → receipt); multiple interface views (voice, dashboards) present this single source of truth
- "Receipts or It Didn't Happen": every tool invocation or model inference produces a structured Receipt capturing full audit trail and verdict; no state mutation without a receipt
- "Cheap-First, Verify-Then-Escalate": lowest-cost approach attempted first; heavier resources only used when verifier flags uncertainty; keeps latency and cost low while maintaining accuracy
- "Ambient Capture, Explicit Action": continuous passive ingestion in parse-only mode; no side-effectful actions without explicit user command; ensures consent and safety
- "Genesis Anchor & Alignment": genesis document encodes purpose and constraints; nightly drift detection ensures system remains true to owner's intent; divergence triggers alerts
- "Apopemptic System" (self-regulating, self-improving): every output feeds back as input somewhere (code answers feed user and media engine, receipts feed coach, engagement feeds prioritization, etc.); creates compounding returns on development effort
- MCP at every boundary is the universal interconnect ("USB-C analogy") enabling vendor-agnostic model routing and tool composition without tight coupling
- The 15 Forge modules are autonomous yet share common architectural principles: ADK coordination, MCP interfaces, Receipt evidence, `entif://` URI scheme, Nx/Nx Cloud, ReasoningBank, GraphRAG+Glyph, Petri/Tripwire, and shared spine services
- 4-hour micro-tier delivery structure creates compounding returns: each deliverable builds on prior ones with immediate utility rather than long waterfall phases
- Parallel workstreams (Core Orchestration + Media Engine) enable independent progress while maintaining integration via shared data models and receipts
- Memory management via nightly Coach jobs (dedupe, merge, taxonomy refinement, TTL/expiration) prevents knowledge bloat while maintaining relevance
- Media & Attention Engine treats "attention as capital" — content dissemination and engagement analytics are feedback loops for system focus and improvement
- Consent & privacy are structural (parse-only ingestion, recording indicator, do-not-ingest list) rather than policy afterthoughts
- All quality gates ("truth fences") are objective and automated; outputs failing red conditions are quarantined until fixed; no subjective bypass

## Contradictions Or Supersession

The enriched doc provided intermediate advancement context but this comprehensive blueprint incorporates and extends all its content. All implementation work referencing Entif 2.0 should use this document as the authoritative source.

**Internal contradictions:**
- Document describes both a "watch folder" approach for ambient ingestion (watch/ directory) and a "webhook via n8n" approach for realtime API feeds; these are presented as alternatives in the same ingestion pipeline. No resolution or selection criteria is given — this is an ambiguity to resolve during implementation planning. (Source: "File/Document Watcher" and "Realtime API Feeds" bullet points in Input & Ambient Ingestion section)

(Source: "Voice-First Orchestrator ('Ada')" section vs. Forge #0 "Ada Forge" entry in Forge Registry)
- Document specifies both "Self-hosted Neo4j" for graph storage and "Postgres + pgvector extension" as alternatives, with ER diagrams for canonical Postgres schema provided in governance docs; no final selection is made. (Source: GraphRAG section and DONOR_FIT_MAP governance doc references)

**Gaps:**

- No specific ASR engine is named — document says "preferably a fast local model for privacy and speed" but doesn't specify which (Whisper, Vosk, etc.)
- No specific embedding model is named for GraphRAG vector similarity search

## Open Questions

- Which ASR engine should be used for Limitless Feed transcription (Whisper, Vosk, or another local model)? What are the latency vs. accuracy tradeoffs for the target use case?
- Which forced alignment tool should be used for LyricsForge alignment (Montreal Forced Aligner, WhisperX, or Gentle)? What is the accuracy requirement?
- Should the graph database be Neo4j (property graph with Cypher) or Postgres+pgvector (SQL with vector extension)? What are the scalability vs. operational complexity tradeoffs for the knowledge graph size expected?
- What OAuth library should be used for SocialForge platform connections (OAuth.NET, oauth4java, or custom)? Should platform tokens be stored in AuthForge vault only or also in platform-specific secure storage?
- Should TRM be implemented as a distilled smaller transformer (custom trained) or as a cached prompt-completion approach using existing small models?
- What is the latency requirement for the "sub-second acknowledgment" of voice commands? Should the VAD + wake-word be local or cloud-hosted?
- How should the "Genesis document" be authored and maintained? Should it be a single markdown file or a structured artifact with versioned sections?
- Should Ada (the voice-first orchestrator) also be a Forge in the registry, or is it the orchestrator that coordinates all Forges (including itself)?
- What is the naming convention for Forge IDs and artifact URIs? Should Forge names use PascalCase (MediaForge) or kebab-case (media-forge) in URIs?
- Should ArticleForge and DocForge be separate Forges or merged into one? They share mechanisms (CI gates, rendering, linting).
