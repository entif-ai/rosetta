## Summary

This document is the most authoritative articulation of Entif's security and governance model, predating NOT LAME by ~6 months. It defines five interlocking systems: (1) a Guard Layer as real-time policy enforcement point between Majordomo and executors; (2) a self-monitoring threat intelligence pipeline with LLM-augmented triage; (3) a Genesis Protocol with HSM-backed multi-sig authority hierarchy; (4) a blockchain-backed decentralization model with tokenomic incentives; and (5) a zero-trust node design for local autonomy. The document also contains extensive implementation ordering (Day 0–10 atomic slices), a financial strategy by maturity phase, and a `Proposed Changes & Additions (delta to your uploaded doc)` section that directly critiques the original plan with specific architectural corrections. Many ideas map cleanly onto existing Rosetta concepts; others represent architectural gaps or design space the system hasn't yet addressed.

## Goals and Intent

- Anchor Entif's agent ecosystem in human-governed, cryptographically-verified constitutional rules
- Prevent any single actor — human, corporation, or AI — from capturing or overriding the system
- Enable local node autonomy without compromising network-wide trust assumptions
- Design cost-control as a first-class architectural property, not an afterthought
- Provide an auditable, tamper-evident ledger of all agent actions

## Components and Technologies

- **Guard service** — TypeScript or Go API, NATS consumer, isolated Kubernetes namespace or cluster
- **OPA / Rego** — policy-as-code engine (Open Policy Agent) for allow/deny rules
- **SPIFFE/SPIRE** — workload identity framework for just-in-time permissioning
- **Firecracker / gVisor** — sandboxed microVM or WASI runtime per task
- **Patrowl** — threat intelligence aggregation framework (CVE, CWE, EPSS, KEV feeds)
- **LLM + embedding service** — vectorizer for threat intel semantic vectors; RAG against SBOM
- **n8n** — workflow automation for feed collection and NATS publishing
- **HSM / YubiKey** — hardware security modules for genesis key ceremony
- **Gnosis Safe or custom multisig** — multi-signature wallet for Genesis key operations
- **Blockchain** — permissioned chain for audit trail (alternative to PostgreSQL append-only)
- **ZK proving systems** — for computation verification without data exposure (future)
- **TPM / Intel SGX / ARM TrustZone** — hardware attestation for node identity
- **Neo4j** — justification graph (existing Rosetta component)
- **NATS** — event总线 (already in Rosetta architecture)
- **OpenTelemetry (OTEL)** — distributed tracing
- **Kubernetes admission controllers** — Volcano admission controller validating Guard tokens
- **MongoDB / object storage** — append-only immutable backup (git + S3 write-once)
- **CISA KEV, NIST NVD, EPSS** — threat feeds

## Conceptual Claims

1. **Majordomo = policy brain (decisions), Guard = referee (enforcement), MCP = context plumbing** — the core role separation that must be preserved as the system scales. Violation of this separation means Guard gets polluted by decision logic and loses independence.
2. **Genesis Protocol is the immutable root of all trust** — nothing (human or AI) runs code or accepts governance directives not signed by the legitimate Genesis authority.
3. **Cryptographic immutability ≠ physical immutability** — even "tamper-evident" logs require active monitoring and independent verification; cryptographic chaining alone doesn't prevent selective withholding of records.
4. **One-way decision tokens prevent escalation cascades** — Guard-signed tokens with nonces are the mechanism that prevents Majordomo from reusing or escalating Guard decisions.
5. **Zero-trust node design is prerequisite for local autonomy** — unless nodes are TPM-attested, sandboxed, and mutually verifiable, local deployments create attack surface the network cannot accept.
6. **Self-monitoring threat intelligence must be a governed subsystem** — the synthesizer's output (candidate rule bundles) must itself be governed and cannot auto-deploy without human multi-sig at high confidence thresholds.
7. **Decentralization ≠ no single point of failure; anti-capture requires explicit constitutional hard-stops** — soft governance constraints (vote to change) can be overridden; structural non-capturability requires timelocks and unanimous multisig for safety-critical changes.
8. **ZKP-based computation verification is the strongest trust model but highest implementation cost** — appropriate for high-stakes verification; overkill for routine task execution where OTEL + Guard decision tokens suffice.

## Dependencies and Sequencing

1. **Immediate (this cycle)**: Guard decision token schema (Day 0) can be defined and committed to `rosetta-schemas` before Guard service exists — schema precedes implementation.
2. **Guard stub (Day 1)**: Isolated Guard service skeleton requires namespace isolation; Kubernetes cluster must support multi-namespace/multi-cluster setup. This maps to Prism shadow-mode implementation.
3. **Executor admission controller (Day 2)**: Volcano admission controller depends on Guard token schema (Day 0) and Guard service (Day 1); Day 2 cannot precede those.
4. **Policy signing + HSM workflow (Day 3)**: Depends on HSM infrastructure; for OSS v1, YubiKey-based test multisig can substitute for production HSM.
5. **Air-gapped red-team sandbox (Day 4)**: Requires separate cluster/VPC; highest infrastructure cost in Day 0–10 sequence.
6. **All later Day tasks (5–10)** depend on prior Days for inputs but maintain independence for parallel team execution.
7. **Blockchain vs. PostgreSQL conflict**: If NOT LAME specifies PostgreSQL as canonical, the blockchain audit trail in this doc is a candidate for deprioritization in favor of append-only PG receipts.

## Contradictions or Supersession

- **Contradiction 1 — Ledger substrate**: Section 4 specifies blockchain as append-only ledger; NOT LAME (April 2026) specifies PostgreSQL as canonical registry. These are mutually exclusive for certain ledger functions. **Determination**: NOT LAME PRD (newer, more specific) supersedes this doc for ledger substrate choice. The blockchain design can be archived as a future scalability option.
- **Contradiction 2 — Tokenomic PoS**: The PoS tokenomics in Section 4 has no counterpart in current Rosetta or NOT LAME scope. **Determination**: This doc's tokenomics should be treated as a separate venture-layer concern, not a requirement for the Rosetta kernel.
- **Supersession — "Proposed Changes" delta section**: The `Proposed Changes & Additions (Delta)` section (lines 80–84) explicitly critiques and corrects the original plan this doc accompanies, representing the refined direction. The delta should be read as the authoritative record where it conflicts with the body above it.
- **Contradiction 3 — MCP role scope**: The preliminary research sections describe MCP as "context-only – never adjudicates actions." Meanwhile, the existing Rosetta MCP package handles skill/tool routing, which includes some action-adjacent decisions. **Determination**: MCP scope is context-anchored; any routing decisions in current MCP are an implementation artifact pending formal Guard-gate enforcement.
